# Be the Cell: levels specification v1.0 (M2 playable slice)

**Status:** ready to implement. This document specifies milestone M2: the level framework, the
Prologue and levels 1.1, 1.2, 1.4 and 1.7, their story beats, completion codes and local
telemetry. It sits beside `docs/ENGINE.md` (physics and engine API, authoritative for both) and
`docs/LAB_UI.md` (the lab screen, authoritative for everything the lab shows). Where this
document needs something from the engine it says so in §8 as a contract; it never redefines
physics. **Instructor:** Alex Foxworthy (they/them). **Repo:** `/home/user/be-the-cell-`
(GitHub `foxworthywa/be-the-cell-`, published at `https://foxworthywa.github.io/be-the-cell-/`).

**Normative words:** MUST, MUST NOT and SHOULD. "Engine spec §x" is `docs/ENGINE.md`, "Lab spec
§x" is `docs/LAB_UI.md`. Numbers marked **[M1]** were measured with engine 1.0.0 in this
session (Appendix A); `tools/level-calibrate.js` (§3.7) re-measures them for engine 1.1 before
release, and the level files read the calibrated values, never the ones printed here. §16
records where the M2 build (1.2, 1.4 and the code tools, engine 1.1.0) departs from this text.

## 0. Summary

- A level is a classic UMD script in `src/levels/` that registers one data object: its text,
  its variant generator, the engine config it runs, its HUD, its predictions, a per-tick
  monitor that decides the goal, its scoring, its debrief, its "Meanwhile, in you" screens and
  the reference and misconception solutions that the tests play.
- One pure level runner (`src/game/`) drives every level through the same phases: story beat →
  task card → prediction → run → result → debrief → "Meanwhile, in you" → completion code.
  Nothing advances because time passed; Continue waits for an answer or an activity.
- The lab screen is reused for runs. A `labConfig` hides names, locks controls, limits speeds
  and adds a 44 px HUD (goal chip, timer, counter). The free-play lab stays one tap away.
- Each attempt gets a per-student variant from a seed (display order, targets, degradation
  rate, sugar schedule), so a shared answer does not transfer.
- Scores combine goal met, efficiency against par, prediction accuracy and first-try debrief
  answers. Behaviour raises misconception flags. A readable completion code with a checksum
  goes into a Canvas quiz; an instructor page decodes codes and verifies run files by replay.
- Telemetry stays on the device and goes into the downloadable run file.
- 1.7 needs the engine's regulation module (LacI, operator, allolactose, lacZYA, CRP–cAMP) and
  the v1.1 adaptation lag. 1.2 and 1.4 run on today's physics. §8 lists every engine need.

## 3. Level definitions (data)

### 3.1 Registration

Each level file ends like this:

```js
// @deps btc-level-kit btc-misconceptions btc-level-constants
(function (root, factory) {
  if (typeof module === 'object' && module.exports) {
    module.exports = factory(require('../game/btc-level-kit.js'), require('../game/btc-misconceptions.js'),
      require('./btc-level-constants.js'));
  } else {
    var B = root.BTC || (root.BTC = {});
    (B.levelDefs || (B.levelDefs = {}))['1.4'] = factory(B.levelKit, B.misconceptions, B.levelConstants);
  }
})(typeof self !== 'undefined' ? self : this, function (K, MC, LC) { 'use strict'; /* … */ return DEF; });
```

`btc-levels.js` reads `BTC.levelDefs`, validates each definition against §3.2 (throws with the
level id and field path), freezes it and exposes `BTC.levels.list` (by `order`) and
`BTC.levels.byId`. In Node, tests `require` a level file directly and pass it to
`BTC.levels.validate(def)`.

**Text lives in data.** Every student-facing string of a level sits in one `TEXT` object at the
top of its file. Functions refer to `TEXT` keys, so text can be rewritten without touching
logic, and the lint (§12.1) walks `TEXT` only.

### 3.2 Schema

| Field | Type | Meaning |
|---|---|---|
| `id` | `'P'`, `'1.1'`, … | Level id |
| `code` | 2 chars | Id in completion codes: `P0`, `11`, `12`, `14`, `17` |
| `order` | int | Position in the level list |
| `version` | int ≥ 1 | Content version. Bump on any change to variants, goals, scoring or questions |
| `title`, `challenge` | TEXT keys | Level-list title and one-line challenge |
| `mode` | `'guided'` \| `'operator'` \| `'designer'` | |
| `scored` | bool | `false` only for the Prologue |
| `los` | `['LO1', …]` | Objectives it gives evidence for (design doc) |
| `misconceptions` | ids | Misconceptions it confronts (§6.3) |
| `estMinutes` | int | Shown on the level list |
| `engine` | `'1.1'` | Engine major.minor it was calibrated for; the constants file must match exactly (§3.7) |
| `phases` | array of phase names | Subset and order from §4.1 |
| `variant(seed)` | pure fn → object | Per-student variant from a 30-bit seed (§4.2). JSON-safe, frozen |
| `config(variant, role, extra)` | pure fn → engine config | `role` is `'task'`, `'demo'` or `'par'`; `extra` carries the design in 1.7. Always sets `config.variant` (§8, R-E3) |
| `labConfig(variant, state)` | pure fn → object | §5.5.1. `state` gives revealed genes and the phase |

| `predictions` | array | Prediction items (§3.3); may reference variant values in templates |

| `monitor(variant, ctx)` | fn → monitor | §3.5 |
| `score(variant, monitorResult, answers, extras)` | pure fn → components | §6.1; `extras` holds demo and par results |
| `flags` | array of up to 8 ids | Bit order in the code's flag byte (§6.4) |
| `debrief` | array of 1–2 questions | §3.3 |
| `echo` | `{screens: [TEXT keys], cards: [{id, title, stamp}]}` | "Meanwhile, in you" (§5.8) |
| `story` | `{intro: [lines], outro: [lines], extra?: {…}}` | §3.3 |
| `narratorRules` | array | Level rules for `BTC.narrate` (§5.5.4) |
| `solutions` | `{reference, …}` | For tests and tools only (§3.6) |

### 3.3 Text items

**Story line:** `{who, text, denies?}` with `who` ∈ `narrator`, `commander` (the player),
`ribosome`, `laci`, `protease`, `glucose`. The UI labels the speaker in small caps ("You" for
the Commander, "The Ribosome", "LacI", "A protease", "A glucose molecule"); there is no
character art. One or two sentences, ≤ 140 characters.

**Question:** `{id, kind: 'choice', prompt, options: [{t, ok?, mc?, fb}]}`.
- Exactly one option has `ok: true`; at least 3 options; every option has `fb`.
- Every wrong option has `mc`, a misconception id from §6.3 (`OTHER` when none fits).
- Option order is shuffled per attempt with `K.rng(variantSeed, 'q:' + id)`, so "the answer is
  B" does not transfer.

**Numeric item:** `{id, kind: 'number', prompt, min, max, step, unit?, answer(variant, extras),
tolerance}` (relative tolerance, e.g. 0.3). Expert only; the student may skip it.

**Sketch item:** `{id, kind: 'sketch', prompt, x: {min, max, label}, y: {min, max, label},
schedule: [{from, to, label}]}` (1.2).

**Truth table item:** `{id, kind: 'table', rows: [{id, label}], cols: [{id, label}], choices:
[two labels], answer: {rowId: {colId: 0|1}}, coreRows(variant), expertRows}` (1.7).

**Lint exceptions.** The lint of §12.1 rejects the teleology regex of Lab spec §7.3, with three
reviewed exceptions:
1. A story line with `who: 'commander'` may match, because the Commander voices the
   misconception. A later line in the same beat MUST have `who: 'narrator'`.
2. A line with `denies: true` may match only if one of `not`, `don't`, `doesn't`, `never`,
   `nothing`, `no one` appears within the three words before the match ("I don't want
   anything.").
3. A wrong option (`ok` absent) with an `mc` tag may match. Its `fb` MUST NOT.

### 3.4 The level kit (`BTC.levelKit`)

Pure, integer-exact where it matters, allowed to use `BTC.prng` and `BTC.math` (it never touches
a cell's streams).

| Function | Behaviour |
|---|---|
| `rng(seed, label)` | An sfc32 stream seeded like the engine's: `splitmix32(seed ^ fnv1a32(label))`, first 12 outputs dropped. Methods `u()` in [0,1), `int(lo, hi)` inclusive (floor of `u()·(hi−lo+1)`), `pick(arr)`, `shuffle(arr)` (Fisher–Yates on a copy) |
| `seedFor(variantSeed, role)` | Engine seed: `fnv1a32(variantSeed + ':' + role) >>> 0` |
| `variantSeed(deviceSeed, levelId, index)` | `fnv1a32(deviceSeed + ':' + levelId + ':' + index) & 0x3FFFFFFF` (30 bits, 6 base32 characters) |
| `fill(template, vars)` | Same as `BTC.format.fill`, available in Node |
| `round(x, step)` | Nearest multiple of `step` |
| `sketch.resample(points, x0, x1, n)` | §5.4.3: x-monotone resampling to `n+1` grid values |
| `sketch.features(s, ref)` | The four shape features of §7.2.6 |
| `sketch.accuracy(s, r)` | Amount accuracy A of §7.2.6 |
| `holdTracker({lo, hi, meanTicks, needTicks})` | Band hold of §7.4.5: `push(x)` → `{mean, inBand, run, best, done, doneTick}` |
| `trailingMean(n)` | Fixed-window mean, `push(x)` → mean |

### 3.5 Monitors

A monitor decides the goal and gathers what scoring needs. It is attached with
`cell.attachRecorder(monitor)`, so the engine calls `monitor.onTick(cell)` after every step: no
engine watchers are needed (§8.2). It reads `cell.observe()` only, never writes, and never uses
wall-clock time, so the same run replayed gives the same result.

```js
monitor = {
  onTick(cell),                 // reads cell.observe(); updates its own plain-JSON state
  end(),                        // null | 'goal' | 'limit' | 'deadline' | 'done' (checked by the runner after each step)
  result(),                     // plain object for score(); includes flags raised by behaviour
  save(), restore(state),       // plain JSON, for the level autosave (§4.4)
  userCommand(entry),           // the runner passes each accepted or rejected user command (LogEntry) here
}
```

The runner drains `cell.takeEvents()` once per frame (as the lab does) and passes them to
`monitor.events(events)` if the monitor defines it. Monitors MUST NOT depend on events for
scoring; they read state (`view.genes[i].functionSeen`, `episode.firstProteinTick`) so the
headless player and replay agree even when events are drained at a different cadence.

### 3.6 Solutions

`solutions` maps a name to a scripted player:

```js
{ kind: 'policy', every: 5, act(view, tick, api) { /* api.command(cmd) as source 'user' */ },
  predictions: {itemId: value}, debrief: {qid: optionId}, design?: {...},
  expect: {goal: true|false, par: true|false, flags?: [ids], minTotal?: number} }
```

`every` is the cadence in ticks (5 ticks, a fast human). `reference` MUST exist and expect goal
and par. Every other solution names the misconception it plays and what it must produce. §12.1
L-4 and L-5 play them.

### 3.7 Calibration constants

`tools/level-calibrate.js` runs the scenarios of each level section ("Calibration") on the
current engine and writes `src/levels/btc-level-constants.js`:

```js
{ engineVersion: '1.1.0', generated: 'YYYY-MM-DD', seeds: 40,
  l11: {...}, l12: {...}, l14: {...}, l17: {...} }
```

- Test L-11 fails when `engineVersion !== BTC.ENGINE_VERSION`, so an engine bump forces a
  re-calibration.
- The tool also runs every reference solution on every variant (or 12 sampled seeds for
  seed-rich variant spaces) with 40 engine seeds and prints the pass rate. It exits non-zero if a
  reference passes goal and par on fewer than 95% of runs, or a misconception solution passes par
  on more than 5%.

### 3.8 Skeleton (1.4, abridged)

```js
const TEXT = {
  title: 'Nothing lasts', challenge: 'Hold a protein level steady while it is broken down.',
  goal: 'Hold LacY between {lo} and {hi} for 10 minutes.', /* … every other string … */
};
const DEF = {
  id: '1.4', code: '14', order: 4, version: 1, title: 'title', challenge: 'challenge',
  mode: 'operator', scored: true, los: ['LO4'], misconceptions: ['MOLECULES_LAST', 'INSTANT', 'CELL_DECIDES'],
  estMinutes: 7, engine: '1.1',
  phases: ['intro', 'task', 'predict', 'run', 'result', 'predict2', 'epilogue', 'debrief', 'echo', 'complete'],
  variant(seed) {
    const r = K.rng(seed, '1.4');
    const halfLife_min = r.pick([3, 4, 5]), targetLevel = r.pick([1, 2]);
    const S = LC.l14.S[halfLife_min][targetLevel], S1 = LC.l14.S[halfLife_min][1];
    return { seed, halfLife_min, targetLevel, lo: K.round(0.70 * S, 10), hi: K.round(1.35 * S, 10), S1: K.round(S1, 10) };
  },
  config(v, role) {
    return { seed: K.seedFor(v.seed, role), strain: 'm1-lab', start: 'birth',
      medium: { glucose_mM: 10, lactose_mM: 0, aminoAcids_mM: 0 },
      genes: { lacY: { level: 'off', kdeg_perS: 0.6931471805599453 / (v.halfLife_min * 60) } },
      flags: { userGenes: ['lacY'] },
      variant: { levelId: '1.4', content: 1, seed: v.seed, halfLife_min: v.halfLife_min, targetLevel: v.targetLevel } };
  },
  /* labConfig, hud, predictions, monitor, score, flags, debrief, echo, story, narratorRules, solutions */
};
```

Every variant object carries its own `seed` (the variant seed). `config.variant` always has
`levelId`, `content` and `seed`, plus the level's variant fields.

## 4. Level flow

### 4.1 Phases and gating

| Phase | Shows | Continue is enabled when |
|---|---|---|
| `scenes` | Prologue scenes (§7.P) | the scene's line is shown and its question, if any, is answered correctly |
| `intro` | The intro story beat, one line at a time | the last line is shown (Skip jumps there) |
| `task` | Task card: goal, Core objectives, Expert objectives | always ("Start") |
| `predict` | Prediction items, one per sheet | every Core item is locked in (Expert items may be skipped) |
| `demo` | 1.2 test run with the sketch overlaid | the demo has reached its end |
| `design` | 1.7 DNA editor | always; "Run" asks for confirmation (§5.10) |
| `run` | The cell, HUD, controls allowed by `labConfig` | the monitor ended the run (`goal`, `limit`, `deadline`, `done`) |
| `result` | Outcome, efficiency against par, prediction review | always |
| `predict2` | 1.4 only: the switch-off prediction | the item is locked in |
| `epilogue` | 1.4 only: switch LacY off and watch 12 game-min | the 12 game-min have run |
| `debrief` | 1–2 questions with per-option feedback | each question answered correctly (retries allowed) |
| `echo` | "Meanwhile, in you" screens and cards | the last screen is shown |
| `complete` | Score and completion code | – (buttons: Copy, Share, Download run, Next level, Levels) |

- Story beats never auto-advance. Every line waits for a tap on "Next".
- A run starts paused (Lab spec §10.3). The player presses Run.
- Pause is always allowed. Commands made while paused apply when time runs (Lab spec §3.4).
- The outro story beat is shown at the start of `echo`, after the debrief, whether or not the goal
  was met. (Shown before the debrief, the outros stated its answers; M2 review, §16.11.)

### 4.2 Attempts, runs, variants and seeds

- **Device seed.** On first launch the app draws one uint32 with `crypto.getRandomValues` and
  stores it in progress (§4.4).
- **Attempt.** A playthrough of one level from `task` to `complete`. Attempt `k` uses variant
  seed `K.variantSeed(deviceSeed, id, k − 1)`. The attempt number is 1 + the number of
  completed attempts. Abandoning and resuming continues the same attempt.
- **Run.** A cell started in the `run` phase. "Try again" after a failed run starts run `n+1`
  of the same attempt: same variant, same engine seed (`K.seedFor(variantSeed, 'task')`), a
  fresh cell. Predictions stay as they were locked. The code reports the attempt and the
  number of runs.
- **Scored run.** The last run of the attempt. First-attempt results are kept separately from
  later ones (§4.4) because the design doc counts first attempts separately.
- **New variant.** "Play again" on the complete screen starts attempt `k+1`.
- **Engine seeds** by role: `'task'` for every run, `'demo'` for the 1.2 demo, `'par'` equals
  `'task'` for the 1.7 par run (common random numbers). The Prologue's live bacterium uses
  `K.seedFor(deviceSeed, 'prologue')` and is not recorded.
- **Think-aloud override.** `?level=1.2&v=<6 base32 chars>` opens that level with that variant
  seed and marks the attempt `override: true` (shown in the code as attempt `0`). The override is
  the level's open attempt until it is completed, so it resumes from its autosave like any other
  (the parameters are taken out of the address once used, §5.11).
- **Runs** are counted up to 99 in the code (`N1`–`N99`); a 100th run still says 99.

### 4.3 Predictions and debrief

| | Predictions (`predict`, `predict2`) | Debrief |
|---|---|---|
| When | before observing | after the run |
| Answer | select, then "Lock in"; can change before locking | tap an option |
| Feedback | none until the result screen; then the chosen option's `fb` beside what happened | the chosen option's `fb` at once |
| Retry | no (one locked answer per attempt) | yes: a wrong option is marked and disabled; the student picks again |
| Scored | the locked answer (§6.1 P) | correct on the first tap (§6.1 D) |
| Flags | the locked option's `mc` | the first tap's `mc` if wrong |

This keeps predict → observe → explain in order (PEDAGOGY rules 1, 4 and 5).

### 4.4 Progress and autosave (`BTC.progress`)

Every access is wrapped in try/catch, as in Lab spec §10.5. The app works when storage throws.

| Key | Contents |
|---|---|
| `btc.progress.v1` | `{v:1, deviceSeed, created: 'YYYY-MM-DD', playerTag: null, cards: {id: true}, prologueSeen, levels: {id: {completed: n, results: [Result], current: CurrentRef|null}}}` |
| `btc.level.autosave.v1` | `{engineVersion, build, levelId, attempt, variantSeed, phase, runs, answers, design, monitor, snapshot, textIndex}` |
| `btc.telemetry.v1` | §11 |
| `btc.ui.v1`, `btc.autosave.v1` | unchanged (the lab's own) |

- `Result` = `{attempt, variantSeed, content, engine, runs, G, E, P, D: [first, total], X, flags,
  total, code, date: 'YYYY-MM-DD', override}`. All results are kept (they are small).
- **Written:** on every phase change, every locked answer, every design change, every accepted
  user command (debounced to at most once per 2 real s), on hide and `pagehide`, and every 60
  real s while running. "Save after every action" (design doc) is met this way.
- **Restored** on load unless `?reset=1`: if `engineVersion` and the level's content version
  (`content`) match, the level reopens at the saved phase; a saved run restores its cell with
  `BTC.Cell.restore(snapshot)` and its monitor with `monitor.restore(state)`, paused, with the
  toast "Resumed level {id}." A 1.2 demo or a 1.7 par run in progress is not saved; it starts
  again from its beginning. A finished demo is rebuilt from its record and shown at its end. A
  mismatched engine or content version discards the level autosave (not the progress) with the
  toast "The app was updated; this level starts again."
- **Two tabs** (or the installed app beside a browser tab) share storage. Every change to the
  progress re-reads the stored copy first (`Progress.sync()`), and the app re-reads it on the
  `storage` event, so neither writes an old copy over the other's codes and attempts. Telemetry
  takes in the other sessions' stored events before it writes. The level autosave stays one slot:
  the last tab to save a level wins.
- Storage can be cleared (iOS clears a site after about 7 days without a visit unless it is
  installed). The complete screen says: "Paste your code into Canvas now; this device may not
  keep it."

### 4.5 Leaving and restarting

A "Levels" button (44 × 44 px, left end of the status strip in levels) returns home. During a
run it asks "Leave this level? It is saved, and you can come back to it." Restarting a level
from its menu ("Start this level again") keeps the attempt and variant and resets phase to
`intro`. The level menu also offers "Replay the story" (shows intro and outro beats) and
"Download this run".

## 5. Screens and interaction

Phone first: 360 × 740 portrait is the primary target; 1280 × 800 must also work. Everything is

#### 5.4.3 Sketch (1.2)
`BTC.Plot` gains the hooks reserved in Lab spec §12 (`setInputMode('sketch', opts)` and
`setOverlay(points, style)`).
- **Layout:** in `compact` the plot fills the content width (328 px) and is 260 px tall; in
  `wide` 640 × 320. Axis labels "LacY (molecules)" and "minutes"; y ticks every 500 up to
  2,000; x ticks every 5 min. A shaded band marks the schedule ("×4 on", 0 to `tOff`).
- **Input:** `touch-action: none` on the canvas while sketching (restored after), pointer events
  with `setPointerCapture`, `pointercancel` handled. Samples map to data units and are clamped
  to the axes.
- **x-monotone capture:** the plot keeps one value per pixel column; drawing over a column
  replaces it (so moving back erases forward). Columns between successive samples of one stroke
  are filled by linear interpolation.
- **Resampling** (`K.sketch.resample`): the grid is `t_j = j · 0.25 min`, `j = 0 … 80`. A grid
  point takes the value of its column; gaps between drawn columns are linearly interpolated;
  before the first drawn column the first value is used, after the last the last value.
- **Coverage:** "Done" is enabled only when the first drawn column is at ≤ 1 min and the last
  at ≥ 19 min; otherwise the prompt reads "Draw across the whole graph."
- Buttons: "Clear" and "Done" (48 px). "Done" locks the sketch.
- **Accessible alternative:** "Use sliders instead" replaces the canvas with five steppers at 2,
  5, 8, 12 and 20 min (0–2,000 in steps of 50); the sketch is the piecewise-linear curve through
  (0, 0) and those points.
- **Overlay:** after the demo, the sketch is drawn dashed in `--muted` over the recorded solid
  line, with the legend "your sketch" / "the cell".

**Hidden-name rules.** With `showNames: false`, everything that could identify a gene across
students follows `displayOrder`: the letter, the card order, the colour (`colorBy: 'display'`),
the locus position on the chromosome drawing, the graph chip order and the narrator's letter.
Glyph shapes stay as they are (membrane rectangle, cytoplasmic circle, LacZ cluster, flagellin
bar), because location and structure are what the student is meant to reason from. Starting
counts are equalised by the level config (§7.1.2). A revealed gene keeps its display colour for
the rest of the level, gains its real name, job and About row, and its card shows "Named after
what its protein did." At `complete`, a list names every candidate.

**Background genes.** Genes outside `genesVisible` keep running. Their proteins are drawn in the
crowd with `--muted` glyphs, keyed "other proteins, not studied here", so colours stay reserved
for the genes in play.

## 6. Scoring and evidence

### 6.1 Components and total

| Component | Symbol | Range | Meaning |
|---|---|---|---|
| Goal met | G | 0 or 1 | The level's Core goal, decided by the monitor |
| Efficiency | E | 0–1 (shown 0–100) | Against par; level formula. **Within par ⇔ E ≥ 0.8** |
| Prediction | P | 0–1 (shown 0–100) | Core prediction items; level formula |
| Debrief | D | first-try right / total | e.g. 1 of 2 |
| Expert | X | bit mask | One bit per Expert objective met |
| Total | S | 0–100 | `S = round(100 · (0.40·G + 0.20·G·E + 0.20·P + 0.20·D_first/D_total))` |

Efficiency counts only when the goal was met, so no single component can be gamed alone. The
Prologue is not scored: its code carries `G1`, `ENA`, `PNA` and its one question in D, and it has
no total. Weights are §14 decision 7.

### 6.2 Par

Par is the performance the level expects from a student who understands the idea. It is stated
per level as a number the student can see in the HUD (target experiments, mRNA budget, number of
setting changes) or, in 1.7, as the reference design run on the student's own schedule.

### 7.1 Level 1.1: "Starving next to a feast"

#### 7.1.1 Summary
Operator mode; LO1; confronts `DNA_DIRECT`, `ENERGY_FIRST`, `PROTEIN_AS_FOOD`,
`PROTEIN_AS_MATERIAL`, `CELL_DECIDES`. Glucose sits outside, and the cell has no working
transporter. Six unlabelled genes; the student finds the one whose protein lets glucose in, in
as few experiments as possible. Names appear only after the protein's function has been seen.

#### 7.1.2 Setup
- Strain `m2-l11` = `m1-lab` plus the decoy gene `araE` (arabinose–proton symporter, membrane,
  role `none`; R-E5). Arabinose is never in the medium.
- `flags.backupGlucoseUptake: true`: a slow side route lets a trickle of glucose in, so the cell
  is starving but not dormant, and every candidate starts from zero on equal footing.
- **Candidates** (visible, names hidden): `ptsG`, `aaImp`, `lacY`, `lacZ`, `fliC`, `araE`. Each
  starts `level: 'off'` with `initial: {clear: true, protein: 0}` (R-E6), so no count reveals the
  transporter. `gly` and `aaSyn` stay on at ×1 as background genes (§5.5.1).
- `labConfig`: `showNames: false`, `displayOrder` from the variant, `colorBy: 'display'`,
  `genesVisible` = the six candidates, `mediumRows: {glucose: 'locked', lactose: 'free',
  aminoAcids: 'free'}` (for the Expert objective), all six dial levels, all five speeds (default 1
  s = 1 min), tabs Cell, Genes, Medium, Graphs.
- Starting state [M1]: after 10 game-min the energy charge is about 0.05 and growth about 0.33 of
  reference; after 30 min 0.07 and 0.27. Engine 1.1 (energy homeostasis) will keep ATP higher;
  the level relies only on R-E7.

#### 7.1.3 Variant
`order = K.rng(seed, '1.1').shuffle(candidates)` (720 orders). Display letters A–F, colours and
loci follow it. Nothing else varies, so the variant is small and each student's "Gene C" differs.

#### 7.1.4 Flow and HUD
Phases: `intro`, `task`, `predict` (p1, p2), `run`, `result`, `debrief`, `echo`, `complete`.

HUD: goal "Find the glucose transporter" → after the reveal "Found it · growth {pct}% of
normal" (progress = λ̄60 / (0.8 λ_ref), capped at 1); timer "{time} left" (limit 180 game-min);
counter "Experiments {n} · target 3".

#### 7.1.5 Goal
- **Experiment:** an accepted user `setPromoter` that switches a candidate from off to on.
  Changing the level of a gene already on does not count; switching it off and on again counts
  again. Medium changes are free.
- **Goal:** `function_seen(ptsG)` has occurred (R-E4), and afterwards the 60-s trailing mean of
  `view.cell.lambda_perS` stays ≥ 0.8 λ_ref for 300 consecutive ticks while ptsG is on.
- **Limit:** 180 game-min. [M1 recovery after ptsG ×1: 57–82 min; ×2: 32–40; ×4: 23.]
- On `function_seen` of any candidate: that gene is revealed (§5.5.1) and the narrator rule
  `l11.reveal` fires. Only ptsG's function can be seen in glucose; aaImp's needs amino acids
  outside, lacY's needs lactose, lacZ's needs lactose and LacY, and fliC and araE never show one.

#### 7.1.6 Scoring
- G as above.
- **E:** `n` = experiments until the goal. `E = clamp(1 − 0.35·max(0, n − 3), 0, 1)` (3 → 1, 4 →
  0.65, 5 → 0.30, 6 → 0). With 4 membrane candidates, reasoning from where the proteins sit gives
  2.5 experiments on average; a random search gives 3.5.
- **P:** mean of p1 and p2 correct.
- **D:** 2 questions.
- **Expert X bit 0:** a second candidate's function is seen and `n ≤ 4` when the goal is met.

**Task card.** Goal: "Get glucose into the cell." Core: "Find the gene whose protein lets glucose
in, and get growth back to normal." · "Use at most 3 experiments; switching a gene on counts as
one." Expert: "Also reveal a second gene's job, with at most 4 experiments in total."

#### 7.1.7 Predictions
**p1** "You switch on the right gene. What changes first?"

#### 7.2.6 Scoring
- **E:** `m` = lacY mRNAs completed from tick 0 to the end of the settle.

- **P (sketch shape):** on the grid of §5.4.3 (`t_j`, 81 points), with `s` the sketch, `r` the
  demo's LacY curve (Recorder `protein:lacY`, linearly interpolated), `s0 = s(0)`, `s20 = s(20)`,

| Feature | Passes when | Misconception if it fails |
|---|---|---|
| F1 delay | `s(1) − s0 ≤ 0.1·(smax − s0)` | `INSTANT` (protein before mRNA) |

| F4 never falls | for every j, `s(t_j) ≥ max_{i≤j} s(t_i) − 0.05·smax` | – (LacY is not broken down here) |

  A flat sketch (`smax − s0 < 100`) fails F1–F3. `P = (F1 + F2 + F3 + F4)/4`. [M1: in the demo,
  60–70% of the final rise comes after the switch-off; the last 5 minutes add 3–8%.]
- **Amount accuracy** (Expert): `A = clamp(1 − mean_{j=1..80} |s(t_j) − r(t_j)| / r(20), 0, 1)`.
- **D:** 2 questions.
- **Expert X bit 0:** the ppm number is within ±30% of the demo's measured `pMade/mMade`.
  **Bit 1:** `A ≥ 0.75`.

**Task card.** Goal: "{T} LacY in the membrane by minute {D}." Core: "Reach {T} LacY by minute

|---|---|

per-student schedule (par is recomputed on it), the randomised prediction rows and option order,

#### 7.7.4 Flow
Phases: `intro`, `task`, `predict` (truth table; Expert: CRP question), `design`, `run`,
`result`, `debrief`, `echo`, `complete`.

- **Par run.** As soon as the variant is known (during `intro`), the runner computes the par run
  in idle frames (≤ 4 ms per frame): the reference design (`wt` lacI, operator present, promoter
  ×1, CRP site present) on the student's schedule with the same engine seed, headless, with the
  same monitor. It is usually done before the student presses Run. If not, the result sheet shows
  "Working out par…" until it is.
- **Run:** starts paused. When the student presses Run, the LacI line (§7.7.11) is shown once.

HUD: goal "Now: {phase word} · {growing | slowed | stopped}" (phase words: glucose, lactose, both
sugars); timer "{elapsed} of 10 h"; counter "No controls" (then the "Run to the end" button).
"Next change: unknown" is shown under the phase word in `wide`.

#### 7.7.5 Measurements (monitor)
With λ̄60 = the 60-s trailing mean of `view.cell.lambda_perS`, `λL = LC.l17.lambdaLacRef` (the
steady growth of the induced wild type on lactose [M1 without regulation: doubling 104 min]),
and lac synthesis `ζ = Σ_{lacZ, lacY, lacA} synthesis_perS · L` (aa/s):

- **Doublings** `Dbl = Σ_ticks lambda_perS · dt / ln 2`.
- **Lag** of an L phase: the first tick `t1` in the phase with λ̄60 < 0.5·λL; if none, lag = 0.
  Otherwise lag = (the first tick after `t1` that starts 60 consecutive ticks with λ̄60 ≥ 0.5·λL)
  − phase start; if none, lag = the phase length. `lag` = mean over L phases.
- **Waste** `wf` = Σ ζ over G-only ticks ÷ Σ `flux.aaPolymerised` over the same ticks.
- **Glucose-first ratio** `rB/L` = mean ζ over the second halves of B phases ÷ mean ζ over the
  second halves of L phases.
- **Lactose growth** per L phase: mean λ̄60 over its second half.
- **Dormancy:** any tick with `dormant` active (event state).

#### 7.7.6 Goal and scoring
- **Goal:** every L phase has lactose growth ≥ 0.5·λL, and the cell is never dormant.
- **E** from three sub-scores against the par run (subscript `ref`):
  - growth `s_g = clamp((Dbl/Dbl_ref − 0.90)/0.08, 0, 1)`;
  - lag `s_l = clamp(1 − (lag − (1.25·lag_ref + 5 min)) / max(lag_ref, 15 min), 0, 1)`;
  - waste `s_w = clamp(1 − (wf − (1.5·wf_ref + 0.001)) / 0.01, 0, 1)`;
  - `E = min(s_g, s_l, s_w)`. The result sheet shows three bars (Growth, Waste in glucose, Lag
    when lactose arrived), each with its par mark, and the 10-hour growth line of the design
    against par (dashed) over the phase bands.
- **P:** fraction of Core truth-table cells right (6 cells).
- **D:** 2 questions.
- **Expert X bit 0 (glucose first):** `rB/L ≤ 0.25`. **Bit 1:** every Expert truth-table cell
  right (all four strains) and the CRP question right.

**Task card.** Goal: "Keep the cell growing through every change, with no controls." Core: "Grow
on lactose in every lactose phase." · "Stay within par for growth, waste and lag; par is the
normal lac genes run on your schedule." Expert: "Glucose first: with both sugars present, make at
most a quarter as much lac protein as on lactose alone." · "Predict all four strains and the CRP
question correctly."

### 8.3 What the v1.1 physics means for level design

- **Energy homeostasis** (ATP stays realistic when sugar is scarce). 1.1's starving cell will keep
  more ATP, so "starving" shows as slow growth and "ATP low" rather than "very low". The goal
  therefore uses `function_seen` and growth, never ATP. Faster responses shorten 1.1; its limit
  (180 min) only gets looser. If the starving cell grows faster than 0.45·λ_ref, 1.1 lowers
  `uBasal_backup` via `config.params`.
- In 1.7, a never-induced design slows almost to a stop on lactose instead of crashing, so the
  goal tests growth in the second half of each lactose phase, not ATP.
- **Adaptation lag.** Every lactose phase is at least 3 × the 90th-percentile wild-type lag
  (`LMIN`, §7.7.3), so the regulated design spends most of each phase growing; the first phase
  is glucose for ≥ 90 min so that constitutive designs have built their enzymes and the wild
  type is repressed. Longer lags lengthen the run rather than making the level unfair. Because
  par is the reference design on the same schedule, any change in lag moves par with it.
- **Lac regulation and waste.** Waste is measured in glucose-only phases, where the wild type is
  repressed and the always-on designs pay. Catabolite repression (CRP) lowers the always-on
  waste, which is why the misconception designs in the tests have no CRP site (§7.7.13).
- **Inducer exclusion** would lower lac expression in "both" phases for every design. If the
  engine models it, calibration must still find `rB/L ≤ 0.25` with the CRP site and ≥ 0.5
  without; otherwise the Expert threshold moves to the midpoint of the two and the level's
  `version` is bumped.
- **Reference state unchanged.** 1.2 and 1.4 run in 10 mM glucose. v1.1 must keep the reference
  calibration (r1 and the g tests as revised) so the [M1] numbers of 1.2 and 1.4 hold within the
  calibration tolerances.
- **New genes in `m2-lac`** add a small burden of their own (LacI ≈ 40 monomers); the preset
  must be regenerated, and the par run absorbs any shift.

## 10. Completion codes (Phase A, no accounts)

### 10.1 Format

One token, hyphen-separated, uppercase, about 60 characters:

```
BTC1-12-7K2Q9C-G1E100P75D12X1-F02-A1N2-R110C1-3F9A0B-4NQ8ZR1
```

```
code    := "BTC1" "-" level "-" variant "-" scores "-F" flags "-A" attempt "N" runs "-R" engine "C" content "-" digest "-" check
level   := "P0" | "11" | "12" | "14" | "17"                 two characters (later: "13", "15", "B0", "21", …)
variant := 6 Crockford base32 characters                   the 30-bit variant seed, big-endian
scores  := "G" [01] "E" num "P" num "D" digit digit "X" hexdigit
num     := 1–3 decimal digits (0–100) | "NA"               E and P in percent, rounded
D       := first-try right, then total (e.g. D12 = 1 of 2)
X       := Expert bit mask, one hex digit
flags   := 2 hex digits                                    the level's flag bits (§6.4)
attempt := 1–3 digits (0 = think-aloud override)          runs := 1–2 digits
engine  := 3 base32 characters: major, minor, patch       "110" = 1.1.0
content := 1–2 digits                                      the level's content version
digest  := 6 hex digits, case-insensitive                  first 6 of the scored run's finalHash ("000000" for the Prologue)
check   := 7 Crockford base32 characters
```

Crockford base32 is `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. Decoding uppercases, maps `O`→`0` and
`I`, `L`→`1`, removes spaces, and accepts `–` or `—` for `-`.

The total is not in the code; the decoder computes it with §6.1. Prologue example:
`BTC1-P0-000000-G1ENAPNAD11X0-F00-A1N1-R110C1-000000-…`.

### 10.2 Checksum

`check` = the top 35 bits of `BTC.math.hash64(utf8(prefix + '|' + SALT))`, in base32, where
`prefix` is the code up to and including the digest and `SALT = 'btc-phase-a-2026'` (a constant
in `btc-code.js`). It catches typos and casual edits. It is not a secret (§10.5).

### 10.3 Copying the code

- The code is shown in an 18 px monospace box with `user-select: all`.
- **Copy code:** `navigator.clipboard.writeText(code)`; if that is missing or fails, select the
  text of a read-only input and `document.execCommand('copy')`; if that fails too, select the
  text and show "Press and hold the code to copy it." Success shows "Copied. Paste it into the
  Canvas quiz."
- **Share** (shown only when `navigator.share` exists): `navigator.share({title: 'Be the Cell
  code', text: code})`; `AbortError` does nothing.
- Every code is kept in progress and listed in "My codes" (§5.1).

### 10.4 Instructor side

**Canvas setup (suggested).** One quiz per level, one "essay" (or "fill in the blank" with no
auto-grading) question: "Paste your Be the Cell completion code for level 1.2." Completion credit
for any valid code of that level (§14 decision 6). For majors, a separate assignment asks for a
code with the Expert bits set.

**`tools/codes.html`** (published at `…/be-the-cell-/tools/codes.html` and runnable from a
checkout by `file://`; it loads `btc-code.js`, `btc-score.js` and the level files):
- Paste codes (one per line) or drop a Canvas "Student analysis" CSV (the tool finds the answer
  column by content and keeps the name column).
- The table: student (from the CSV), level, variant (and its decoded values, e.g. `T 500, tOff
  5`), G, E, P, D, X (named objectives), flags (named), attempt, runs, engine, content, total,
  valid ✓/✗ with the reason (bad checksum, unknown level, unknown content version).
- Warnings: the same code from two students; the same variant seed from two students; an
  override attempt (0); a code whose engine differs from the current build.
- "Download CSV" of the table.
- **Run file check:** drop a run file (§11.4) to replay it (below) in the page.

**`node tools/decode-codes.js <file.csv | codes.txt> [--csv out.csv]`** prints the same table.

**`node tools/verify-run.js <run.json>`** replays the scored run record with the level's monitor
attached (R-E18), recomputes E, the sketch or table scores from the stored answers, the flags,
the total and the code, and reports "match" or each difference. It also verifies the 1.2 demo
record and recomputes the 1.7 par run.

### 10.5 What a code cannot guarantee

- **Who played.** There are no accounts; a code can be passed to a friend. Duplicate codes and
  duplicate variant seeds are flagged, but a unique code from someone else is not detectable.
- **An honest score.** The salt and the algorithm are in the public page, so anyone who reads it
  can make a valid code with any score. The checksum only catches typos and casual edits.
- **That the play happened in this app,** unmodified, on the engine and content it names.
- **A first attempt.** Clearing site data or using another browser starts again at attempt 1.
- **Re-verification without the run file.** Only a run file can be replayed; with it, replay
  shows that the run and the score match, still not who made it.
- **Comparability across content versions.** Codes from different `C` values may differ in
  variants or scoring.
- **Survival on the device.** Codes kept only on an uninstalled iPhone may be cleared after about
  a week without a visit.

Phase C (server replay, LTI 1.3) replaces the code with verified submissions.

## 11. Local telemetry

### 11.1 Principles

- Stored on the device only, in `localStorage`. The app still makes no network requests.
- It leaves the device only in files the student chooses to send: a level run file or "Export my
  data".
- No names, no free text (except the optional player tag, §14 decision 4), no absolute
  timestamps except the session date.
- Written through `BTC.telemetry.log(type, data)`; failures are ignored.

### 11.2 Event schema

```js
{ v: 1, seq, s: 'a1b2c3d4',   // session id: 8 hex from crypto.getRandomValues at app load
  t: 123456,                  // integer ms since session start (performance.now), never Date
  lv: '1.2' | null, att: 1 | null, run: 2 | null,
  tick: 1234 | null,          // engine tick when a cell is involved
  type: 'predict', d: { … } }
```

| type | d |
|---|---|
| `session_start` | `{date: 'YYYY-MM-DD', build, engine, layout, w, h, standalone, touch, reducedMotion}` |
| `screen` | `{name}` (home, lab, level, codes, cards) |
| `level_start` | `{variantSeed, content, variant}` (the variant object) |
| `phase` | `{name}` |
| `story` | `{beat, line, action: 'next' \| 'skip'}` |
| `predict` | `{id, kind, value, correct}`; sketch: `{id, points: n, features: [F1…F4], A, P}` (the points themselves go in the run file) |
| `design` | `{part, from, to}`; `design_submit {design}` |
| `demo_end` | `{ppm, final}` |
| `run_start` | `{speed}`; `run_end {reason: 'goal' \| 'limit' \| 'deadline' \| 'done' \| 'retry' \| 'leave', ticks}` |
| `cmd` | `{seq, type, args, ok, code?}` (user commands only; the engine log has the rest) |
| `speed`, `pause`, `resume`, `tab`, `focus` | `{s}`, `{}`, `{}`, `{name}`, `{gene}` |
| `reveal` | `{gene, letter}` |
| `goal` | `{}` (tick set) |
| `flag` | `{id, evidence}` |
| `debrief` | `{id, option, correct, try}` |
| `echo` | `{screen}`; `card {id}` |
| `score` | `{G, E, P, D, X, total}` |
| `code` | `{code, action: 'shown' \| 'copied' \| 'shared' \| 'copy-failed'}` |
| `download` | `{kind: 'run' \| 'export'}` |
| `error` | `{msg}` (no stack) |

### 11.3 Storage

`btc.telemetry.v1 = {v: 1, events: [...]}`, a ring buffer of at most 5,000 events and about 512
KB; on a quota error the oldest half is dropped and the write is tried once more.

### 11.4 Files

**Level run file** ("Download this run", complete screen or level menu), named
`be-the-cell-<level>-<variant>-a<attempt>.json`, delivered like the lab's (Lab spec §4.5):

```js
{ format: 'btc-level-run', v: 1, build, ui: {layout, speedHistory},
  level: { id, content, variantSeed, variant, attempt, runs, override,
           design?, answers: {itemId: value}, sketch?: [[t, y], …], debrief: [{id, option, try}],
           result: {G, E, P, D, X, flags: [{id, tick?, data}], total}, code },
  records: { task: <runRecord of the scored run>, demo?: <runRecord>, par?: {finalHash} },
  telemetry: [ …events with this lv and att… ] }
```

**Export my data:** `{format: 'btc-export', v: 1, progress, telemetry}`.

## 15. Open items and risks

1. **1.7 depends on the regulation module and the adaptation lag** (R-E13, R-E15). If the lag
   comes out above 60 min, lactose phases grow and 1.7 lasts longer in real time at a given
   speed; the default speed may need to be 1 s = 1 h. *Resolved in the build (§16.8): lactose
   phases of 245–260 min after both sugars, runs of 14–18 game-h, 1 s = 10 min by default (about
   a minute and a half of real time), and "Run to the end".*
2. **Noise.** 1.2's mRNA count and 1.4's band hold are stochastic. The calibration pass rates
   (§3.7) are the guard; failing variants are widened, not hidden.
3. **Par run on slow phones.** 36,000 ticks at ≈ 50 µs is ≈ 2 s of engine time, spread over idle
   frames during the intro and prediction. Measure on the test Chromebook; if it is too slow,
   precompute par only when the student presses Run and show "Working out par…".
4. **Facts checked before release** *(done: the M2 biology review verified them, §16.11)*: about
   3.0 × 10¹³ human cells (Sender 2016); red blood cell life about 120 days; GLUT4 and SGLT
   wording; AraE (P0AE24, 472 aa), LacA (P07464, 203 aa) and LacI (P03023, 360 aa) lengths; LacI
   about 10 tetramers per cell; Oehler 1990 repression factors; two insulin gene copies.
5. **Palette:** two new gene colours need the CVD check that U-5 was deferred for. *Done:
   `tests/ui-palette.test.js` (§16.10).*
6. **Sketch fairness across devices:** a finger on a 360 px plot is coarser than a mouse. The
   metric uses tolerant features and a 0.25-min grid; think-aloud sessions should compare phone
   and laptop sketches (a pilot success criterion).
7. **Integrity** is weak by design in Phase A (§10.5).
8. **Size:** if the bundle passes 750 KB, add a safe comment-stripping step to `build.js`
   (tokenizer-based; never regex over code). With 1.2 and 1.4 it is 790 KB; whole-line comments
   are about 120 KB of the scripts. Levels 1.1 and 1.7 will pass 900 KB without it. *Decided
   (§16.9): the limits are now 1.5 MB (fail) and 1.2 MB (warn), with no comment stripping; the
   bundle is about 920 KB with all five levels.*
9. **1.4 stockpile at half-life 5 min, ×2:** the stockpile holds the band on 6 of 40 seeds there
   (2.5% over all variants). A longer hold or a narrower band would close it at the cost of the
   `single` rate (95%). *Decided (§16.9): that variant is removed (content version 2); the
   stockpile now reaches the goal on 0.5% of runs.*
10. **1.3 and the priming threshold:** engine 1.1 has no bootstrapping threshold (§16.1). 1.3
    needs a new way to show that an ATP-starved cell cannot make the enzymes that make ATP (for
    example a finite medium or a lower gate), decided before it is specified.
11. **1.7 and the lag:** the wild-type lag is 125–146 min, not 20–60 (§16.1). The options in
    ENGINE.md §15 item 1 stand: accept 2-h lags (L phases ≥ 3·lagP90 ≈ 7 h), start every L phase
    after a both-sugar phase (lag 64–71 min), or ask for a reserve in a later engine. *Decided
    (§16.8): every L phase follows a both-sugar phase, and L ≥ 3·lagP90 on those schedules.*

### 16.2 Framework (runner, schema, kit)

- **`config.variant` always passed.** The `src/game` fallback that rebuilt a cell without
  `config.variant` after a `ConfigError` is removed; `makeCell(config)` is `new Cell(config)`.
- **Demo monitor.** `def.demo.monitor(variant)` gives the demo cell a monitor with the run
  monitor's interface (`start`, `onTick`, `result`, `save`, `restore`); `demoResult(v, cell,
  monitorResult)` receives its result. During the demo the HUD reads it (`{demo: true, …}`) and
  the level narrator rules see it as `level.monitor`.
- **The demo runs by itself** (`startPaused: false`) at 1 s = 1 min on the Graphs tab (Protein
  with the sketch overlaid, then mRNA; fixed 20-min axis). Pause stays allowed. At 20 min a
  sheet shows the sketch over the test run's curve, the four features ✓/✗, the amount accuracy
  and the measured copies per mRNA, with "Continue to your run".
- **The epilogue starts on the student's tap** ("Switch LacY off" sends the logged user command
  and calls `runner.startEpilogue()`), not on entering the phase; until then the phase is halted.
  A headless solution plays it with `epilogue.act`.
- **Alternative outros.** `story.extra` (named beats) and `outroKey(variant, monitorResult,
  goal)`: the outro's first line must be true of the run the student just made (1.2: `keptOn`,
  `missed`; 1.4: `pulsed`, `missed`). Validated with the other beats.
- **Run monitors start from the cell** (`start(cell)`), so the HUD shows the newborn's LacY
  before the first tick, as the gene card does.
- **Pure helpers** in `BTC.game`: `answerRecord`, `debriefFromTaps`, `summarise`, `monitorFeed`
  (shared by live runs and replays), `verifyRunFile`, `checkExpect`. Headless play gives a Core
  sketch or number that a solution does not script the reference prediction.
- **`labConfig` additions:** `plots` (which plots, in order), `graphWindow` (s; a window that is
  not a preset hides the Window row), `initialTab`. `yBand` is drawn on the Protein plot.
- **HUD additions:** `goal.short`, `timer.short`, `counter.short` (used below 400 px) and
  `goal.gauge {lo, hi, max, value}` (1.4's band gauge). Whole minutes left round up ("due in 9
  min" at 5 min 30 s of a 14-min deadline). The HUD is 44 px in the wide layout too (M1 build;
  §5.5 says 40 px), so its buttons keep 44 px targets.
- **Completion screen:** "Expert {a} of {b}" (objectives met) instead of the bit mask of §5.9
  ("Expert 3" read as a score); the code still carries X. A predict phase with one question is
  titled "Predict", not "Prediction 1 of 1".
